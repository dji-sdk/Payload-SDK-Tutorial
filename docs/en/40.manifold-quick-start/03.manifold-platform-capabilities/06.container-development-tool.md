
Manifold 3 includes a controlled container management toolset (`box-*` commands) that wraps Docker under the hood and exposes security-restricted commands. Developers can use container capabilities without root privileges. All commands follow docker conventions. Permissions, resources, ports, and file mounts inside containers are pre-configured by the platform, while image contents and naming are the developer's responsibility.

## Basic Description

The `box-*` commands wrap Docker internally. The naming convention is `box-<docker subcommand>`, corresponding **one-to-one** with docker subcommands, but only a security-whitelisted subset is available. Direct use of the `docker` command is not supported. Key capabilities include:

- Creating and managing development containers
- Entering containers for development and debugging
- Saving, exporting/importing, and pulling custom environment images
- Passing through host physical devices (USB-Serial / cameras / GPIO / I2C / PSDK USB, etc.)
- Running Python, AI inference, and model validation programs inside containers
- Using NVIDIA GPU for inference

The system includes pre-built official base images such as `box-dev` (development) and `box-dpk` (service), which can be used directly.

:::warning Note:
- The system does not expose the `docker` command. All container operations must be performed through `box-*` commands.
- Containers run as root inside the container, allowing dependencies to be installed and files inside the container to be modified directly. Containers are isolated from the host, so root privileges inside the container do not apply to the host. On the host side, you still use your own login account, and host root privileges are not provided.
- Host networking is disabled by default. For PSDK and other scenarios that require the same network view as the host, you can explicitly enable it with `--network host` (see [box-run](#box-run)).
- Each user can only manage containers and images they have created.
- The `/workspace` directory inside the container is bidirectionally mounted with `~/box/workspace` on the host. Data in other paths is lost when the container is removed (run `box-commit` beforehand to preserve it).
- When a container exits abnormally, Docker will automatically restart it (the platform pre-configures `--restart=unless-stopped`).
:::

:::tip Note:
Any `box-*` command supports `-h` / `--help` to view full help information (including option descriptions, restrictions, exit codes, and examples).
:::

## Container and DPK Relationship

Container (Docker) and DPK are mutually exclusive deployment modes. Choose one based on your use case.

| Scenario | Description |
|:---|:---|
| DPK | Lightweight application packages, easy to distribute. Packages can be installed, uninstalled, started, and managed through Pilot, directly accessible to end users. |
| Docker Container | For deep customization or project-specific scenarios. Can be packaged as Docker images for distribution and batch installation. Requires system console access to configure images or install software. Intended for developers or professional delivery teams. |

:::warning Note:
1. When using DPK deployment, it is not recommended to simultaneously run PSDK programs inside Docker containers, as port conflicts may occur.
2. When using Docker containers to develop PSDK applications, it is not recommended to simultaneously use DPK deployment, as Pilot may be unable to install and manage DPK applications properly.
:::

:::tip Running PSDK Programs
Before running a PSDK program inside the container, pass through the corresponding USB channel to the container. Then you can run compiled PSDK executables directly inside the container, such as `dji_sdk_demo_on_manifold3`, which is compiled in the <a href="../quick-demo.html#run-the-demo" target="_blank">Run the Demo</a> section. The pass-through method depends on the PSDK connection scheme:

- **USB bulk scheme**: The build output is located in `build-manifold3-usbbulk/`. Use `--functionfs` to pass through the FunctionFS endpoint directory, and add `--network host`. For details, see "PSDK USB Pass-through (`--functionfs` + `--network host`)" in [box-run](#box-run).
- **Serial scheme**: If the external device is a character device, such as `/dev/ttyACM0`, pass it through with `--device`.
:::

## Core Concepts

Container development involves the following core concepts. Understanding them helps with using the subsequent commands:

| Concept | Description |
|:---|:---|
| Image | A read-only environment template containing the system, dependencies, and configuration required for execution. It can be compared to a *class* in object-oriented programming and is not itself executable. The system includes official images such as `box-dev` and `box-dpk`. Custom images can be obtained via `box-pull`, `box-load`, or `box-commit`. |
| Container | A running instance created from an image, comparable to an *object* instantiated from a *class*. Containers are writable and isolated from one another; development and debugging are performed within containers. |
| Commit | Saving the current state of a container (e.g., installed dependencies) as a new environment image for future reuse, equivalent to saving a configured environment as a new template. Image names can be customized. |
| Workspace | A shared working directory between the container and the host. Data persists even after the container is removed (see *Workspace Directory* below). |

### Workspace Directory

| Location | Path |
|:---|:---|
| Host | `~/box/workspace` (actually located on the large-capacity partition `/open_app/workspaces/<user>/box/workspace`; `~/box` is a symlink to this directory) |
| Container | `/workspace` |

- Files placed in the workspace are **bidirectionally visible** between the host and the container.
- Host files outside the workspace are not accessible from within the container.
- Files stored in other container paths (e.g., `/tmp`) are lost when the container is removed with `box-rm`. To preserve them, run `box-commit` before removal.

### Ports

Only ports in the range 20000–20100 can be exposed. The host and container port numbers are identical, and they are bound only to `127.0.0.1` (not reachable from outside the device).

## Typical Workflow

The following example demonstrates a complete container development workflow:

```bash
# 1. Log in to the device with your account
#    Accounts with UID >= 1000 and an interactive shell are automatically added to the boxusers group during provisioning

# 2. Start a development container
box-run --name mydev box-dev:0.1

# 3. Enter the container
box-exec -it mydev -- bash

# 4. Develop inside the container
pwd                          # /workspace (auto-mounted to your ~/box/workspace)
python3 --version
pip install requests

# 5. Exit the container and save the environment
exit
box-commit mydev myenv:1     # freely named

# 6. Start a new container from the saved image (start directly by image name, consistent with docker run)
box-run --name dev2 myenv:1
box-exec dev2 -- python3 -c "import requests; print(requests.__version__)"

# 7. Clean up
box-stop dev2 && box-rm dev2
box-stop mydev && box-rm mydev
```

Cross-device image distribution workflow:

```bash
# Device A: Export the image
box-save my-image:1
# -> ~/box/exports/my-image_1.tar
# (The command output shows the actual path pointed to by the symlink, such as /open_app/workspaces/alice/box/exports/my-image_1.tar)

# Copy to Device B (replace target path with the corresponding user's home directory on Device B)
scp ~/box/exports/my-image_1.tar <bob>@deviceB:/home/<bob>/

# Device B: Load the image from any readable path
box-load /home/<bob>/my-image_1.tar
# -> Image my-image:1 is now available on Device B

# Device B: Use the image directly
box-run my-image:1
```

## Command Reference

### box-run

Create and start a new container.

```bash
box-run [--name NAME] [-p PORT] [--gpu auto|none] [--gpus GPU_SPEC] [--device DEV] [--functionfs FFS_DIR] [--network host] <image>:<tag> [-- command [args ...]]
```

**Parameters**

| Parameter | Required | Description | Example |
| :-- | :-- | :-- | :-- |
| image | Yes | Image name. Must include a tag, in the format `<image>:<tag>` (official / box-commit / box-load / box-pull outputs). | box-dev:0.1 |
| --name | No | Container name. Auto-generated if not specified. Must follow the naming rules (see "Container Naming Rules" below). | --name mydev |
| -p, --publish | No | Port mapping. Host and container port numbers are identical. Range: 20000-20100. Bound to `127.0.0.1` only. Mutually exclusive with `--network host`. | -p 20080 |
| --gpu | No | GPU mode (legacy syntax): `auto` (default) or `none` | --gpu none |
| --gpus | No | Docker-style full GPU syntax pass-through (`all` / `none` / `device=0` / `count=N`) | --gpus all |
| --device | No | Pass through a host device (can be specified multiple times). Must be an absolute path under `/dev/` (see "Device Pass-through" and "GPU Usage" below). | --device /dev/ttyUSB0 |
| --functionfs | No | Pass through a host FunctionFS (USB gadget) endpoint directory (can be specified multiple times). Used specifically for PSDK USB bulk scenarios (see "PSDK USB Pass-through" below). | --functionfs /dev/usb-ffs/bulk2 |
| --network | No | Only accepts `host`, allowing the container to share the host network namespace (`--net` is an equivalent alias). Bridge, none, and custom networks are not supported. | --network host |

:::tip Note:
- The workspace is automatically mounted to `/workspace` inside the container (corresponding to `~/box/workspace` on the host).
:::

:::tip Container Resource Limits (platform pre-configured; cannot be overridden via command-line parameters)

| Resource | Limit |
|:---|:---|
| Memory | 12 GB |
| CPU | 6 cores |
| Shared Memory (SHM) | 1 GB |
| Process Count (PIDs) | 512 |
| File Descriptors (nofile) | Soft 1024 / Hard 2048 |
| User Processes (nproc) | 1024 |

If your workload requires higher resource limits, contact your device operations team to adjust the `box.conf` configuration.
:::

**Container Naming Rules**

A container name specified via `--name` must meet the following rules, otherwise it will be rejected:

- Must start with a letter or a digit.
- Subsequent characters may include: letters (`a-z`, `A-Z`), digits (`0-9`), underscore (`_`), dot (`.`), and hyphen (`-`).
- Must not contain spaces, colons (`:`), slashes (`/`), Chinese characters, or special characters such as `@`, `#`, `$`.
- Length must be 2–64 characters.
- The container name must be unique and cannot conflict with existing container names.

| Type | Examples |
|:---|:---|
| Valid | `mydev`, `test-1`, `test_1`, `test.1`, `A123`, `my-app_v1.0` |
| Invalid | `-test` (starts with a hyphen), `g` (too short), `my:app` (contains a colon), `my/app` (contains a slash) |

**Examples**

```bash
# Minimal startup
box-run box-dev:0.1

# Specify container name + port mapping
box-run --name web -p 20080 box-dpk:0.1

# Disable GPU
box-run --gpus none box-dev:0.1

# Device pass-through + GPU + port combination
box-run --device /dev/ttyACM0 --gpus all -p 20088 my-app:1

# Start from a custom environment image and execute a command
box-run myenv:1 -- python3 main.py
```

**Device Pass-through (`--device`)**

When a container needs to access host physical devices (such as USB-Serial, USB cameras, GPIO, or I2C), use the `--device` parameter to pass the device through to the container.

```bash
# Pass through a single device
box-run --device /dev/ttyUSB0 my-image:1

# Pass through multiple devices (repeatable)
box-run --device /dev/ttyACM0 --device /dev/bus/usb/001/004 my-psdk-app:1

# Device + GPU + port combination
box-run --device /dev/ttyACM0 --gpus all -p 20088 my-app:1
```

Constraints:

- The path must be an absolute path under `/dev/`
- Must be a character device or block device. Regular files and directories are rejected.
- **Blacklisted devices** (to prevent container misoperations from damaging the device; cannot be overridden): `/dev/mem`, `/dev/kmem`, `/dev/sd*`, `/dev/nvme*`, `/dev/disk*`, `/dev/loop*`, `/dev/kvm`, `/dev/port`
- Symlink paths are automatically resolved to their real paths before validation; the blacklist cannot be bypassed.
- Containers have default read-write permissions on passed-through devices, but cannot create new device nodes inside the container.

**PSDK USB Pass-through (`--functionfs` + `--network host`)**

The PSDK USB bulk scheme, whose build output is located in `build-manifold3-usbbulk/`, uses the USB gadget FunctionFS interface. Its pass-through method is different from that of normal character devices:

```bash
# PSDK USB bulk container (--network host and --functionfs are both required)
box-run --name psdkdev --gpus none --network host \
        --functionfs /dev/usb-ffs/bulk2 \
        --functionfs /dev/usb-ffs/bulk3 \
        box-dev:0.1
```

Before running the PSDK program, make sure the executable exists in the workspace. The container can access only `/workspace`; other host directories are not visible. If it has not been compiled, refer to <a href="../quick-demo.html#run-the-demo" target="_blank">Run the Demo</a> to compile it first, or use `box-cp` to copy the compiled output to `~/box/workspace/`:

```bash
# Confirm that the program exists (adjust the path based on your actual project directory)
box-exec psdkdev -- ls -l /workspace/payload-sdk/build-manifold3-usbbulk/bin/

# Run the PSDK program
box-exec psdkdev -- sh -c 'cd /workspace/payload-sdk && ./build-manifold3-usbbulk/bin/dji_sdk_demo_on_manifold3'
```

FunctionFS endpoints must be passed through with `--functionfs`, not `--device`: endpoints (`ep0` / `ep1` / `ep2`) are regular file nodes on the ffs filesystem, not character or block devices. Passing them through with `--device` will be rejected with `not a char/block device`. This is a normal validation result and does not mean the path is incorrect.

Constraints:

- Pass the ffs **mount point directory itself**, such as `/dev/usb-ffs/bulk2`, instead of `ep0` / `ep1` / `ep2` under it.
- Wildcards are not supported. Specify each path explicitly.
- The channel number is determined by the PSDK program's endpoint configuration. For the Manifold 3 USB bulk scheme, both `bulk2` and `bulk3` must be passed through. Missing either channel causes PSDK initialization to fail. You can view the currently available channels with `ls -d /dev/usb-ffs/bulk*`.
- `--network host` is required. Without it, PSDK cannot establish communication with host-side services.

:::warning PSDK USB Notes
- **Do not stop the host-side `usb_bulk_raw` process**. This process must remain resident. Once stopped, endpoints under `/dev/usb-ffs/` disappear immediately, and PSDK inside the container stops working.
- The host-side PSDK program and the PSDK program inside the container must not run at the same time. Only one PSDK client should exist at any given time.
- If a large number of `Bad file descriptor` logs appear after PSDK starts inside the container, `--functionfs` or `--network host` is usually not specified correctly. Check each item against the command above.
:::

**Host Network (`--network host`)**

The container shares the host network namespace, so its network view is identical to the host's network view. For example, host network interfaces such as `usb0` are visible, and host local services are accessible.

```bash
# Use host networking
box-run --name hostnet --network host box-dev:0.1

# --net is an equivalent alias
box-run --name hostnet2 --net host box-dev:0.1
```

Constraints:

- Only `host` is accepted. `bridge`, `none`, and custom network names are rejected.
- Mutually exclusive with `-p` / `--publish`: with host networking, the container directly shares the host port space, so ports do not need to and cannot be published.
- Processes inside the container can listen on any idle host port and are **no longer restricted to the 20000-20100 port range**. Avoid system service ports such as sshd, dockerd, and other system services; occupying them can affect host services.
- `ping` works normally inside the container, the same as containers using the default bridge network.
- `CAP_NET_ADMIN` is still not granted, so the host network configuration cannot be modified inside the container.

**GPU Usage (Jetson Platform)**

Manifold 3 is equipped with the Jetson Orin platform. `box-run` enables GPU for containers by default, requiring no additional parameters.

```bash
# Enable GPU by default (the following three forms are equivalent)
box-run --name g1 --gpus all box-dev:0.1
box-run --name g2 --gpu auto box-dev:0.1
box-run --name g3 box-dev:0.1

# Explicitly disable GPU (for CPU-only workloads)
box-run --name g4 --gpus none box-dev:0.1

# Specify GPU capability set
box-run --name g5 --gpus 'all,"capabilities=video,compute"' box-dev:0.1
```

Using CUDA inside the container:

```bash
# 1. Pull the full image
box-pull nvcr.io/nvidia/l4t-pytorch:r35.2.1-pth2.0-py3

# 2. Start the container in the background, using sleep infinity to keep it running
box-run --name torch-cuda --gpus all nvcr.io/nvidia/l4t-pytorch:r35.2.1-pth2.0-py3

# 3. Enter an interactive shell in the container (if your local ssh has a TTY, -it works; without a TTY only -i is available)
box-exec -it torch-cuda -- bash

# 4. Verify CUDA inside the container
python3 - <<'PY'
import torch
print("torch:", torch.__version__)
print("cuda:", torch.cuda.is_available())
print("device:", torch.cuda.get_device_name(0) if torch.cuda.is_available() else "No CUDA")
PY
```

**Common Messages and Their Meanings**

| Symptom | Meaning |
|:---|:---|
| `[box-run] note: GPU requested, but docker daemon has not enabled nvidia runtime` | The device has not enabled GPU runtime. The container can still start but cannot use the GPU. For CPU-only workloads, add `--gpus none` to suppress this message. If GPU is needed, contact your operations team. |
| `GR3D_FREQ 0%@0` | The GPU is currently idle. This is normal. |

### box-exec

Execute a command inside a running container.

```bash
box-exec [-it] [--user U] [--workdir W] <container> -- <command> [args ...]
```

**Parameters**

| Parameter | Required | Description | Example |

:::tip box-kill vs. box-stop Comparison

| Command | Signal | Behavior | Use Case |
|:---|:---|:---|:---|
| `box-kill` (no `-s`) | SIGKILL | Immediate kill, no wait | Container is unresponsive |
| `box-kill -s TERM` | SIGTERM | Sends signal, does not wait for exit | Trigger graceful shutdown and monitor manually |
| `box-stop` | SIGTERM + SIGKILL | Sends TERM first, auto KILL after 10s | Normal container shutdown (recommended) |

### box-load

Load an image from a tar file.

```bash
box-load <file_path>                   # Preserves the original image name from the tar
box-load <file_path> --as <repo>:<tag> # Explicitly specify a new image name
```

**Parameters**

| Parameter | Required | Description | Example |
| :-- | :-- | :-- | :-- |
| file_path | Yes | Path to the tar file. Must be readable by the current user. Can be placed in `~/box/imports/` (scp-friendly), or any path readable by the current user. | ~/box/imports/my_env.tar |
| --as | No | Explicitly specify the image name after loading (defaults to preserving the original name from the tar) | --as my-env:1 |

Image loading is subject to the following constraints:

- The file must be readable by the current user (the platform verifies readability using the current user's identity; reading other users' files is rejected).
- The file must be in docker save format (containing manifest.json metadata).
- Compressed tar files are accepted by default.
- The tar layer limit defaults to 256 layers (can be adjusted by administrators via `box.conf` `IMPORT_MAX_LAYERS`). PyTorch/CUDA full images typically have 30–50 layers, well within this limit.
- The tar must not contain device nodes / fifos / sockets / absolute paths / `..` path traversal.
- The loaded image name defaults to the original name from the tar. Use `--as` to explicitly rename.

**Examples**

```bash
# Load from the imports directory (recommended location, scp-friendly)
box-load ~/box/imports/my_env.tar

# Load from any readable path
box-load /tmp/nginx.tar
box-load /home/alice/local-build.tar.gz  # Compressed tar accepted (absolute paths recommended)

# Load and rename
box-load /tmp/nginx.tar --as my-nginx:v1
```

## Usage Restrictions

### Docker Commands Not Provided and Alternatives

The following docker subcommands are not available on this platform as corresponding box commands:

| Docker Command | Alternative |
|:---|:---|
| docker push / login / logout / search | The device does not manage registry credentials. To push images, use your own Docker credentials in an external environment. |
| docker build / docker builder | Use `box-run` to enter a container, prepare the environment manually, then `box-commit` to save as an image. |
| docker import | Use `box-load` (follows the `docker load` protocol with image metadata validation). |
| docker export | Use `box-save` (exports at image granularity). |
| docker create | `box-run` combines creation and startup. |
| docker info / version / system df | For Docker/kernel versions, see `BUILD_INFO.txt` / `ENV_INFO.txt`. For images and containers, use `box-images` + `box-ps -a`. |
| docker network * / docker volume * | Networking uses the default bridge + single-port `-p` pass-through, or `--network host` to share the host network. Data uses `~/box/workspace` (auto-mounted). |
| docker port | Covered by the PORTS column in `box-ps` + `box-inspect`. |
| docker events / update / attach | Use `box-exec -it` as a replacement for `attach`. |
| docker system prune / container prune / image prune | Use `box-rmi` to clean up images individually. |
| docker plugin / compose / swarm / node / service / secret / config / context / buildx / trust / manifest / stack / checkpoint | These subsystems are not introduced in the controlled environment. |

### Commonly Rejected Operations

The following operations are not accepted by the platform and will be rejected:

```bash
docker xxx                        # permission denied (use box-*)
sudo docker xxx                   # not allowed
box-run --name g box-dev:0.1     # container name "g" is only 1 character; Docker requires >= 2 characters
box-run -v /etc:/etc             # unknown option (workspace is auto-mounted)
box-run --privileged             # unknown option
box-run --cap-add SYS_ADMIN      # unknown option
box-run -p 80                    # port not in allowed range (20000-20100)
box-run --network bridge         # --network only accepts host
box-run --network host -p 20080  # --network host is mutually exclusive with -p
box-run --functionfs /dev/usb-ffs/bulk2/ep1   # pass the ffs mount point directory, not an ep file under it
box-run --device /dev/usb-ffs/bulk2           # ffs endpoints are not character/block devices; use --functionfs for PSDK
box-run --device /dev/nvme0n1    # device is blacklisted (disk / memory / loop / kvm devices)
box-run --device /etc/passwd     # not a character device / block device
box-commit mydev myenv           # missing tag; must be written as myenv:<tag>
box-stop other-users-container   # not the current user's container
box-load /root/secret.tar        # current user cannot read this file (platform verifies readability as the current user)
box-cp /etc/shadow devbox:/tmp/x # host-side path must be within ~/box/{workspace,exports,imports}/
box-cp -L src dst                # -L not accepted
box-rmi -f <image>               # force removal not allowed; use box-stop + box-rm on the container first, then box-rmi
box-rmi box-dev:0.1              # removing a factory image requires the --confirm flag to prevent accidental deletion
box-exec -it mydev -- tegrastats # tegrastats is a Jetson host tool, not available inside the container; run it on the host side
```
